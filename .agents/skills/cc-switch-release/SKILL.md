# CC Switch Windows 发布

只用于 `cloud-wyf/cc-switch`，先验证当前仓库身份。执行前完整阅读 [Windows 发布规范](../../../docs/guides/local-release.md)；该链接相对本技能目录，命令均从项目根目录执行。

## 授权与范围

- 用户的实际发布指令授权完成本次提交、正常推送 `main` 与 Tag、GitHub 构建签名及 Release 发布；先简述本次版本和变更范围，再连续执行，不逐步索取重复确认。
- “总结发布流程”不等于“现在发布”。只要求修改代码、只提交/推送时遵循用户限定。
- 混有无法判断归属的修改、分支或远程不符合约定时，先核对上下文，不能把所有文件盲目纳入提交。

## 执行顺序

1. 检查工作区、合并状态、`origin/main`、已有 Tag/Release 和工具链；保留所有本地修改。
2. 按实际已发布/已占用版本确定新版本，同步四处版本号、四语应用内摘要和中文发布说明。
3. 完成对应范围的验证。前端回归与 Rust 大型编译错开；已有同源码检查结果可复用。
4. 明确暂存本次文件，提交；有 `MERGE_HEAD` 时完成真实合并提交。创建新 Tag，正常推送`main` 和该 Tag，核对远程 SHA。
5. 查找并复用同 Tag/SHA 的云端任务；默认不取消 Tag 推送已启动的发布。用户明确要求本机发布时，才取消同版本活动任务并确认结束。
6. 预检通过后准备绑定确切 SHA 的 Release 草稿与说明，用 `pnpm release --tag ...` 触发或等待 GitHub 编译、签名、验签和上传，必须等任务结束。云端失败保留任务日志和草稿，不自动转本机；打 Tag 后修源码须换新修订号。本机发布的缓存复用和恢复按规范执行。
7. 确认 Release 已发布，下载六个附件核对 SHA-256、签名和三个 Windows 更新入口；记录结果并给出版本链接。

## 不变量

- 不移动已有 Tag，不覆盖已发布版本；同源码未发布草稿才可重试。发布过程修改了源码，则重新验证并使用未占用的新版本。
- 沿用已有私钥和应用公钥，凭据不输出、不进 Git；不自动安装、启动新版或迁移日常数据库。
- 使用现有 `scripts/release.mjs`、`windows-release.mjs` 和 `validate-release.mjs`，不绕过其源码一致性与签名检查。
- 只有远程核验完成才报告全部完成；失败时报告已完成阶段、失败原因和恢复方式。
